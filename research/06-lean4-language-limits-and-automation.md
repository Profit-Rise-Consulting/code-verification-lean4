## A. Language reference (lean-lang.org) — accessed 2026-11-07

A1. Reference manual covers Lean 4.36.0-rc2. https://lean-lang.org/doc/reference/latest/ [primary]
 "Lean is an interactive theorem prover based on dependent type theory, designed for use both in cutting-edge mathematics and in software verification." "...Lean is also a pure functional programming language, with features such as a run-time system based on reference counting ..., multi-threading, and monadic IO." "The core type theory is implemented in a minimal kernel that does nothing other than check proof terms."
 Chapters include: grind, vcgen, mvcgen (17,18), IO (22), Iterators, Validating a Lean Proof.
A2. IO intro https://lean-lang.org/doc/reference/latest/IO/ [primary]
 "Lean is a pure functional programming language. ... the order of evaluation that is used during type checking ... is formally unspecified ... Including side effects such as console I/O, arbitrary mutable state, or random number generation would violate this principle."
 "Many of the basic side effects, such as reading from files, are opaque constants from the perspective of Lean's logic. Others are specified by code that is logically equivalent to the run-time version."
 Sections: Logical Model, Control Structures, Console, Mutable refs, Files, System, Env, Timing, Processes, Random Numbers, Tasks and Threads, Asynchronous Programming.
A3. IO logical model https://lean-lang.org/doc/reference/latest/IO/Logical-Model/ [primary] (via fetch-extractor summary; quotes short)
 IO α "a description of a process"; state monad over "the entire world"; world not in memory, "an abstract token that stands for its state"; BaseIO (no exceptions) / IO = EIO IO.Error / EIO ε.
 Without "clearly-marked unsafe operators" no way to extract pure value from IO; "there is no way for values to 'escape'".
 Possibly nonterminating programs must be `partial`; logically arbitrary constants.
A4. Tasks and Threads https://lean-lang.org/doc/reference/latest/IO/Tasks-and-Threads/ [primary]
 Task α: "a computation that, at some point, will resolve to a value of type α"; Task.spawn pure; thread pool sized by LEAN_NUM_THREADS or logical processors; "not a hard limit"; priorities 0..8 + dedicated; dropping last reference cancels pure Tasks; IO.asTask tasks continue unless they poll IO.checkCanceled; IO.cancel is cooperative. Page does not characterise tasks as (non)deterministic.
A5. Timing https://lean-lang.org/doc/reference/latest/IO/Timing/ [primary]
 IO.sleep, IO.monoNanosNow/monoMsNow are `opaque` ("Monotonically increasing time since an unspecified past point... no relation to wall clock time"). Heartbeats = "number of 'small' memory allocations" used for "deterministic" timeouts. (No real-time/WCET model in page.)
A6. Random numbers https://lean-lang.org/doc/reference/latest/IO/Random-Numbers/ [primary]
 IO.rand (pseudorandom, seedable via IO.setRandSeed), RandomGen/StdGen pure generators, IO.getRandomBytes "opaque ... Reads bytes from a system entropy source. It is not guaranteed to be cryptographically secure."
A7. Run-time code https://lean-lang.org/doc/reference/latest/Run-Time-Code/ [primary]
 "The Task API provides the ability to write parallel and concurrent code. The runtime is responsible for scheduling Lean tasks across operating-system threads." Sections: Boxing, Reference Counting, Multi-Threaded Execution, FFI.
A8. Recursive definitions: partial/unsafe https://lean-lang.org/doc/reference/latest/Definitions/Recursive-Definitions/ [primary] (extractor summary)
 partial: no termination proof, "all that is required for soundness is that their return type is inhabited"; kernel treats as "opaque constants", "neither unfolded nor reduced"; "their equational theory in Lean's logic is simply very weak".
 unsafe: no restrictions; any declaration referring to unsafe must be unsafe; compiled code can be replaced with efficient variants "while the kernel still uses the original definition"; incorrect unsafe impl can make program diverge from the verified logical model though "logical soundness is not at risk".
 Termination: structural / wf recursion / partial_fixpoint / coinductive_fixpoint / inductive_fixpoint clauses exist.
A9. Axioms https://lean-lang.org/doc/reference/latest/Axioms/ [primary]
 Standard: propext, Classical.choice, Quot.sound; sorryAx. "In addition to the standard axioms, proofs by native evaluation introduce a dedicated axiom for each computation ... These axioms track proofs that depend on the correctness of the entire compiler, and not just on the much smaller kernel." native_decide creates e.g. bigSum._native.native_decide.ax_1 : decide (...) = true. Axioms "do not reduce"; compiler cannot generate code for axioms.
A10. Validating a Lean Proof https://lean-lang.org/doc/reference/latest/ValidatingProofs/ [primary]
 Escalation: blue check marks -> #print axioms -> lean4checker --fresh -> comparator (+ nanoda external checker, sandbox). Remaining issues listed: "The soundness of Lean's logic", comparator plumbing/sandbox, "no implementation bug affecting all of the used checkers", "No human error or misleading presentation of the theorem statement".
 Distinguishes "does the theorem have a valid proof" from "what does the theorem statement mean". Defines "malicious" to include "un-reviewed AI-generated proofs and programs".
 Section "On Lean.trustCompiler (up to Lean 4.28.0)": native computation via decide +native / bv_decide; "Specific uses wrapped in honest tactics (e.g. bv_decide) are generally trustworthy. The trusted code base is larger (it includes Lean's compilation toolchain and library annotations in the standard library), but still fixed and vetted."
 decide docs: "+native ... at the cost of increasing the size of the trusted code base. Namely, it depends on the correctness of the Lean compiler and all definitions with an @[implemented_by] attribute."
A11. grind https://lean-lang.org/doc/reference/latest/The--grind--tactic/ [primary] (extractor)
 "techniques inspired by modern SMT solvers"; congruence closure, linear integer arithmetic, commutative ring solver; Fin arithmetic. Not bitvectors: for "bit-level or pure Boolean combinatorial problems" use bv_decide (CaDiCaL/Kissat). Limitation: "not designed for goals whose search space explodes combinatorially" (pigeonhole, graph colouring, N-queens, 200-var Sudoku).
A12. mvcgen https://lean-lang.org/doc/reference/latest/The--mvcgen--tactic/ [primary] (extractor)
 "monadic verification condition generator" for do-notation programs; page says it "has been superseded by vcgen", which "supports a wider variety of proofs and performs better". Import Std.Tactic.Do.
A13. bv_decide: Lean 4.12.0 release notes https://lean-lang.org/doc/reference/latest/releases/v4.12.0/ [primary]
 "It reduces the goal to a SAT instance that is refuted by an external solver, and the resulting LRAT proof is checked in Lean... proofs generated by this tactic use Lean.ofReduceBool, so this tactic includes the Lean compiler as part of the trusted code base. The external solver CaDiCaL is included with Lean".
A14. bv_decide source doc (lean4 repo) https://github.com/leanprover/lean4/blob/b35cb10cf2ced51a2fd1880cfdbf75c71ab7a35a/src/Lean/Elab/Tactic/BVDecide.lean [primary]
 Steps: by_contra, bv_normalize (subset of Bitwuzla rewrites), reflection, verified bitblast to AIG, CNF, CaDiCaL -> LRAT, verified LRAT checker; "If CaDiCal returns SAT ... presents a counterexample". sat.timeout default 10 s. "debug.skipKernelTC ... essentially trusts the SAT solver". "adds the result of the compiled check as an axiom, thus adding the Lean compiler to the trusted code base." Also supports uninterpreted functions over BitVec/Bool via CEGAR (Syntax.lean).
A15. Reservoir LeanSAT (deprecated) https://reservoir.lean-lang.org/@leanprover/leansat [primary]; reference 4.23 bitvectors page https://lean-lang.org/doc/reference/4.23.0/Basic-Types/Bitvectors/ [primary]: "The resulting proofs rely only on the axiom Lean.ofReduceBool; the external prover is not part of the trusted code base."
A16. Release list: https://lean-lang.org/doc/reference/latest/releases/ [primary]: latest 4.36.0-rc2 (2026-10-27); 4.35.0 (2026-10-12); 4.34.0-rc1/4.33.0 (2026-08-10, per leanprover.cn mirror); 4.29.0 (2026-03-27); 4.29.1/4.28.1 (2026-04-14); 4.28.0 (2026-02-17); 4.27.0 (2026-01-24); 4.26.0 (2025-12-13); 4.25.0 (2025-11-14).
A17. Secondary changelog https://kt3k.github.io/changelog/leanprover/lean4/2026-10-20 [secondary]: 2026-10-20 commits: lia divisibility, grind soundness/normalization fixes, "vcgen +jp" join points "turns branch-explosion from exponential to linear".

## F. Concurrency/Task evidence
F1. Zulip "Deadlocking the task system" https://leanprover-community.github.io/archive/stream/270676-lean4/topic/Deadlocking.20the.20task.20system.html [primary-community, 2023]: Mac Malone: "you are waiting on a task from within another task, which worthlessly consumes a thread in the thread pool and is a known pitfall with tasks in Lean".
F2. Zulip "structured concurrency" https://leanprover-community.github.io/archive/stream/270676-lean4/topic/structured.20concurrency.html [primary-community]: two kinds of tasks (pure vs IO); "`Task`s are just standard futures available in virtually any stdlib, not structured concurrency".
F3. GitHub issue #1280 Additional concurrency primitives https://github.com/leanprover/lean4/issues/1280 [primary]: "Lean only has a single concurrency primitive right now, Task... you can't easily use it to achieve mutual exclusion"; "IO.Refs use busy waiting in case of concurrent modifications" (as of issue time; since then Mutex/Condvar/Channel exist per F5).
F4. Zulip "Task code not running in parallel" https://leanprover-community.github.io/archive/stream/270676-lean4/topic/Task.20code.20not.20running.20in.20parallel.html [primary-community, Feb 2024]: LEAN_NUM_THREADS discussion.
F5. scidonia/leanin docs/lean-concurrency-today.md https://github.com/scidonia/leanin/blob/main/docs/lean-concurrency-today.md [secondary; third-party analysis, Lean 4.35]: "Lean 4.35 already ships a Tokio-shaped surface — tasks, promises, async/await, cancellation contexts, channels, semaphores, a select protocol, timers, TCP/UDP, DNS and an HTTP server, all on a libuv reactor — but underneath ... a single global priority thread pool with no work-stealing ... and none of it is verified." "no machine-checked work-stealing deque, scheduler, or scheduling bound exists in Lean, and no formal semantics of Lean's IO/Task exists at all [R]". "No ThreadSanitizer instrumentation ... no deterministic scheduler hook". Program logic `Std/WP/**` "4.35 only, sequential". Measurements: 64×IO.sleep 100 = 801 ms; 64×Async.sleep 100 = 102 ms on 8 cores.

## G. Async, probabilistic, roadmap
G1. Async reference https://lean-lang.org/doc/reference/latest/IO/Async/ [primary] (extractor): Async/EAsync/BaseAsync over Task+Promise; "Calling `await` on a task never blocks an OS-level thread"; selection randomized for fairness; "`race` ... computations whose results are not used are not canceled"; "If the task is never awaited, the error vanishes"; cancellation cooperative; TCP/UDP/DNS async; "Receiving in parallel on the same TCP socket is unsupported"; "stopping a timer can leave a task awaiting it hanging forever".

## Open Questions (not answered by the evidence gathered; for Phase 2)
1. Does any Lean-based tool connect a protocol-level model (e.g. Veil, LeanDA transition systems) to a real executable implementation with a machine-checked refinement, rather than to a Lean model of the code? Evidence so far shows Veil verifies Lean-embedded transition systems (J1) and Aeneas translates Rust to a pure Lean model (K2); the exact formal link between model and deployed binary was not examined.
2. What is the formal semantics of Lean's IO/Task in the logic? F5 (third-party) claims none exists; A3 describes IO as a world-passing model with opaque primitives. Neither the Std.Do/vcgen documentation extract (A12) nor its successor was read in enough depth to say which monads/effects (IO, Task, Async) are supported by weakest-precondition reasoning.
3. Does vcgen/Loom/Std.Do support nondeterminism, interleavings or concurrency in the program logic? G4 states Loom's monad-transformer library encodes "non-determinism"; F5 states the sequential-only status of Std/WP. No primary Lean-doc statement on concurrent reasoning was found.
4. Are liveness/fairness properties supported in Lean-based protocol tooling? J1 says Veil safety now, liveness "in the future"; I12 and I11 are third-party. No Lean-native temporal-logic library was surveyed.
5. How is the "implemented_by"/@[extern]/FFI boundary handled in trust-reporting (does #print axioms or comparator flag it)? A9/A10 mention native evaluation axioms and implemented_by dependence for decide +native only; behaviour for ordinary compiled code that is never proved about was not documented in sources read.
6. Exact status and numbers of Lean-auto/Duper benchmarks (C2 figure truncated) and Lean-SMT finite-field results (URL not retained). Needs re-fetch.
7. Mathlib/Batteries coverage for BitVec, ByteArray, finite maps beyond Std was not systematically inventoried (only Std.HashMap lemma coverage and release-note mentions were read). Mathlib size figures are slide/blog claims (G9, I9), not a measured count.
8. Real-time/WCET: no source found addressing timing properties of Lean programs beyond API docs (A5) and one third-party measurement (F5). Unknown whether any Lean project verifies timing.
9. Proof-maintenance cost: only anecdotal/practitioner (I7, I8, K6) and release-note breaking-change lists (B-series, I5). No quantitative study of proof breakage per Lean release was found. RELEASES.md quote (I6) is from an older snapshot; current compatibility policy is unclear (H1 says none stated; G6 lists "stabilize Lean components to guarantee backwards compatibility" as a Year-4 goal).
10. Zulip coverage is thin: only archived threads on Tasks/concurrency (F1, F2, F4) and the verifier thread (G10) were read. Searches for threads on "Lean for protocol verification" or "Lean is not suited for..." surfaced no primary community statements; the suitability statements found are secondary (I9, I11, I12, I15).
11. Several benchmark and trust claims come from 2026 preprints not independently validated (D-series, E-series, K2); results on math benchmarks (D) were obtained with Lean 4.9.0 (D1, D2) – far older than current Lean.
12. Versions 4.31 and 4.33 release notes and 4.25-4.27 notes were not read individually.
